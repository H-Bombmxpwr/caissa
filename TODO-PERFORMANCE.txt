===============================================================================
HOW EACH ONE WAS FIXED
===============================================================================

SORT BY RATING — a generated column
  The sort key was an expression, MAX(COALESCE(white_elo,0),COALESCE(black_elo,0)),
  and no index can answer an expression, so ten million rows were sorted to return
  thirty. games.top_elo is now that expression given a name:

      ALTER TABLE games ADD COLUMN top_elo INTEGER
        GENERATED ALWAYS AS (MAX(COALESCE(white_elo,0),COALESCE(black_elo,0))) VIRTUAL

  Being generated it cannot drift and no insert path has to set it; being a column
  it can be indexed. Costs 120 MB. min_elo now reads it too — "either player at
  least this" is exactly what it holds.

  Watch out: PRAGMA table_info does NOT list generated columns. Use table_xinfo, or
  the migration adds the column again on every launch.

OPENING DROPDOWN — a summary table
  /api/openings did GROUP BY opening over every row, per keystroke. There is now an
  opening_summary table (name, eco_from, eco_to, games) — 806 rows for this library.
  It is maintained incrementally: add_games folds in the openings it just imported
  rather than recounting, and attach_reference rebuilds once at the end because ten
  million increments are worse than one pass. A library that has never had one gets
  it built in the background on first ask, so the box never blocks.

FREE-TEXT BOX — indexed above 200,000 games, unchanged below
  Eleven LIKE '%term%' columns cannot use an index. On a small library that is
  instant and it usefully matches a forename in the middle of "Carlsen, Magnus", so
  below 200,000 games nothing changed. Above it the box resolves through indexes:
  names, tournaments and ECO codes match from the START of the value, and opening
  names still match anywhere inside — via opening_summary, because "Najdorf" sits in
  the middle of what that opening is called.

  What it gives up: a forename, or a word from the middle of a tournament name. Those
  fields in the Filters dialog still search anywhere, and the search box says so
  while a narrowed search is showing.

  Measured before choosing this over FTS5: the indexed path found 5,145 of the 5,158
  games the scan found for "Carlsen" — 99.7% — in 0.9 s against 39 s. FTS5 would
  have bought the last 0.3% for about 1.5 GB and half an hour of build time.

OPENING NAME FILTER — the same summary
  opening LIKE '%Sicilian%' scanned. It now matches names in opening_summary (a few
  hundred rows) and finds the games by indexed equality on games_opening (+96 MB).
  The summary only ever gains names, so it cannot miss a match.

===============================================================================
NOT WORTH DOING — measured, decided against
===============================================================================

POSITION-INDEXING THE BASE. Do not.
  One row per half-move: 68 rows a game at 113 bytes. For 10.36M games that is
  ~700 million rows and ~79 GB, plus hours. Index the collections you carve out
  instead — a thousand games is ~7 MB and takes seconds, and that is what the
  explorer, the position context panel and the Player Lab actually read.

  ChessBase does not do this either. Its search booster (.cit/.cib) is a per-game
  signature — material and structure — used to discard most games cheaply and then
  decode the survivors. A filter, not an index, which is why it costs hundreds of
  bytes a game rather than 7 KB. If whole-base position search is ever wanted, that
  is the design to copy, and it is a feature in its own right.

  (ChessBase details are from its documented structure and observable behaviour, not
  from reverse-engineering the format.)

FTS5 FOR THE SEARCH BOX. See above: 0.3% more results for 1.5 GB and half an hour.
  If it is ever wanted, the shape is an external-content FTS5 table over the name,
  event, site and opening columns, kept in step by triggers, built the way the
  reference scan is — in resumable passes.

VACUUM after big deletes. The space is reused. It also needs an exclusive lock a
  running app denies; it hung for 12 minutes here.

===============================================================================
THINGS THAT WILL BITE AGAIN IF FORGOTTEN
===============================================================================

- One-time migrations must record that they ran. Two backfills in Library.__init__
  re-derived "nothing to do" with a full scan on every launch — 50 seconds once the
  base was attached. They write a 'backfill:<name>' marker into settings now. Any
  future one-time job should. Tests that simulate an old library must clear the
  marker, which test_chessbase and test_library_tools now do.

- A background thread that outlives a test's temp library stops the folder being
  deleted on Windows. The opening summary rebuilds inline below 50,000 games and
  only takes a thread above that, which is why the suite is clean.

- Deleting reference rows is slow ONLY because of foreign-key cascade checks. With
  nothing referencing them, PRAGMA foreign_keys=OFF turned 15 minutes into 49
  seconds for 775k rows. Verify nothing references them first.

- Timing the API from a script: use 127.0.0.1, never localhost. "localhost" resolves
  to IPv6 first here and costs a flat 2 s per request. It looks exactly like a
  server problem and is not one.

- Leftover test servers. Four of mine on ports 8791-8794 held 2.3 GB and were the
  main reason long scans kept being killed for memory.
  netstat -ano | grep LISTENING | grep :88

- The first search after launch is slower than the numbers above: it reads index
  pages off a 7.2 GB file. After that the OS cache holds them. Measure warm.
